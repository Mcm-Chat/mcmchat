## Persistence and multi-device contract

The settings write path now uses the account-checked `update_my_settings` RPC instead of client read/merge/write. Server-side JSON patches must merge each section, including individual `voice.custom` parameters, under a row lock/upsert so disjoint changes survive simultaneous devices. Same-field concurrent updates remain last acknowledged writer wins. `getSettings` must tolerate first-login row creation racing on two devices without replacing a winning row with defaults.

The shared settings hook resets data on account changes, ignores outdated responses, coalesces in-flight reads and refreshes on focus, online, visible resume and periodic visible polling. This is eventual convergence, not guaranteed immediate realtime replication. Device permissions, OS channels, audio routing and local animation choices are deliberately device-specific. Successful preference persistence cannot grant an OS permission or configure a third-party service.

Automatic push resume now calls `refresh_my_push_device`: it updates an existing non-revoked installation owned by the authenticated account, returns no device credentials and does not insert or re-enable a device. `enablePush` from an explicit user action remains the registration/re-enable path. The notification-permission row distinguishes OS permission from registration and exposes that explicit action when permission is already granted.

This work does **not** claim to solve the existing global token-uniqueness race in concurrent explicit device registration. The refresh path refuses a token already observed on another device/account, but independent-session contention and the existing explicit registration path still need a dedicated production-compatible uniqueness/ownership test and, if necessary, a separate schema change.

Roll out both migrations in order **before** the frontend that calls their RPCs:

1. `supabase/migrations/20261026180002_atomic_user_settings.sql` — account-checked atomic partial settings updates.
2. `supabase/migrations/20261026180357_push_refresh_preserves_revocation.sql` — refresh-only push registration updates that preserve revocation.

If either RPC is absent/denied, show an explicit failure or unregistered state; do not fall back to unsafe settings read/merge/write or revive a revoked device through automatic registration. Validate grants, ownership, RLS and rejection of unsupported keys/types on a separate test database before production use. The new Android app-settings bridge also requires an APK rebuild; a web deployment cannot add that native method to an already installed APK. Neither production migration nor APK rollout has been performed here.
